### The board

By default the board is **team**: the squad's members as rows, the selected member's detail and the latest replies beside them, and the lead's notes below. Press `/` and type to narrow the rows. A <Waiting /> marks a member that's waiting on you, and those rows sort first. Every key works from what's already on screen; slow lookups such as pull request status refresh in the background. The board reloads within about a second when a member, request or room changes, or when you edit `squad.toml`, and it still refreshes on its interval (`refresh`, or `"off"`) for everything else. Press **ctrl-r** to refresh at once, even while you search or type a message. `tmt sq ls` prints the member list as text, or as JSON with `--json`, and it's what `tmt sq` shows when there's no terminal. `tmt sq board` always opens the board.

### Token rate

The Team layout shows the squad's token rate at the right of the summary line, such as `1.2k tok/s 1m ▂▅▇▃`. It adds up the tokens of requests that finished in the window across members, so it moves in steps as requests finish, not while a model is writing. Press **w** to cycle 5s, 1m (the default), 30m and 1h; until a window has filled, its label shows the time covered so far. `0` means no finished requests, `≥` means some members could not be read, and the meter is hidden when no member reports usage. Members whose driver never reports usage are listed under `?`. The bars show the trend: `▁` is zero and a blank is no data.

Turn it on or tune it under `[board.token_rate]` for every squad, or `[squad.<name>.board.token_rate]` for one:

<Code>{`
[board.token_rate]
enabled = true
window = "1m"         # 5s, 1m, 30m or 1h
every = "5s"          # how often it samples, 5s to 10s; the 5s window needs 5s
reduced_motion = false
`}</Code>

### Tabs: one per squad

The first line of the board holds its tabs: one per squad, plus two built in. **leads** lists every squad's lead in one place, and **all** has one row per squad with its lead, its member count and what needs you. Enter on a row in **all** opens that squad's tab.

Every tab starts with a two-cell mark: `◆` when a member waits on you, `✗` when one is blocked, or blank. The count follows the name, such as `◆ product 2`, and a blocked count is added when both apply: `◆ product 2 ✗1`. Only the mark and the `✗` count carry the attention colors, so the state never depends on color alone. The tab you're on keeps its accent name and count, and the selection background covers the whole tab; other tabs' names and counts are muted. ← and → switch tabs, and **s** opens a switcher over every tab, hidden ones included, that narrows as you type. When there are more tabs than fit, the line scrolls to keep the current one in view and counts the tabs off each end (`‹ 3`, `5 ›`), colored by the most pressing one it hides.

A tab you've opened before shows at once and refreshes in the background. One you haven't opened keeps the previous view until the new one is ready, and if that takes more than a moment, `⠋ loading` appears on the summary line. Switch again and the old load is dropped.

Shift+← and Shift+→ move the current tab, and dragging a tab onto another's place moves it there. The board writes the new order to your config and changes nothing else in the file:

<Code>{`
# ~/.config/tmux-team/squad.toml
[tabs]
order = ["all", "leads", "product"]
hide  = ["quiet"]                      # still reachable with s, or tmt sq board --squad quiet
`}</Code>

### Board views

A view arranges panes and their initial folds. It keeps the squad's states, rows, providers, reminders, token meter and theme. List the five factory views with `tmt sq view ls` (or bare `tmt sq view`):

| View   | Arrangement                                                                                                                           |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| team   | The default arrangement: rows beside detail and replies, with full-width lead notes below. Detail and replies fold below 100 columns. |
| focus  | Rows fill the board above folded detail, replies and notes titles.                                                                    |
| notes  | Rows take 35% beside lead notes at 65%; detail and replies start folded below them.                                                   |
| detail | Rows above detail and replies, with notes folded; replies also folds below 100 columns.                                               |
| wide   | Rows, detail/replies and notes in three columns at 40/30/30; detail/replies fold below 180 columns.                                   |

<Cmd>{`
$ tmt sq view set notes                      # all boards
$ tmt sq view set wide --squad product       # this squad
$ tmt sq view rm --squad product             # inherit the arrangement
`}</Cmd>

A hand-written `board.layout` or `panes` for a squad always wins, then that squad's `view`, then `[board] view`, then the workflow layout's own arrangement. `view set` changes only the `view` key and refuses a file that changed meanwhile; with `--squad` it also refuses a hand-written layout, so remove that yourself first. `view rm` removes only `view`, so custom layouts and folds stay. Folds you make by hand keep their usual session rules.

### Panes: rows, notes and replies

The board is made of panes: **rows** (the list above), **notes** (the lead's own `tmt notes`, read-only), **detail** (the selected row) and **replies** (the latest answers from the lead and members). Show the ones you want, split side by side, stacked top and bottom, or as tabs you flip between.

The notes pane shows the lead's own notebook, the file `tmt notes path --identity <lead>` prints. There is no separate squad notebook, and the board never creates one: a lead without a notebook shows `(no notes yet)`, and a temporary lead can't keep one. Leads keep a short **Current state** section at the top, with **Now**, **Next** and **Blocked** in a few lines, so the board shows what the squad is doing.

In split mode, press **d** to fold or unfold detail and replies together (if either is open, both fold). Click a pane's title to toggle just that one. The footer shows the state: `d detail+replies ▾` (open) or `d detail+replies ▸` (folded). A folded pane shrinks to its `▸ name` title and its neighbours take the space; unfolding brings back the sizes you set. Tab skips folded panes. Folds last for the session, per squad, and never change your config; a manual fold wins over automatic narrow-width folding. Tabs mode doesn't fold.

To start with a pane folded, add `collapsed = ["detail"]` under `[squad.product.board]`. To toggle other panes with a key, bind it, such as `D = "toggle notes"` or `d = "toggle detail replies"`; pane names must be known and unique.

<SplitBoardSketch />

<Caption>Sketch: rows and notes side by side, with an annotation being typed.</Caption>

- **Annotate a row.** Press `a` and type. The note goes to the lead, tagged with the row, for example `[product · auth-fix] keep old tokens valid for a day`. The row shows `✎ sent to sol` until the lead answers, so you can see what you've raised and what's still open. The lead decides what to do with it: update the board, add it to its notes, or pass it to the member.
- **Member context.** Use `task=` for what a member is doing and `pending=` for what it waits on you for; longer context goes in the member's own notebook (`tmt notes path --identity <member>`). A note set by an older version is hidden, and `note=` with an empty value clears it.
- **Detail shows every column.** Besides the member's task and links, the detail pane lists the full value of every other board column, in column order. Long values wrap instead of being cut; a failed field shows `?` and a missing value `–`.
- **Notes read like notes.** The notes pane renders common Markdown: headings, lists, bold and italic, inline code and links. Anything else shows as plain text. Lines wrap to the pane, wide characters like Chinese stay aligned, and terminal escape codes are removed. You never edit the lead's notes from the board, so they keep one author.
- **Replies stay complete.** Available reply bodies use the notes pane's safe Markdown styles and wrap without a line cap. Prompts wrap too. Focus replies to scroll with arrows or j/k, PgUp/PgDn and Home/End, or use the wheel over the pane. Older replies without a loaded body keep their `tmt result <id>` hint; reading and scrolling acknowledge nothing.

### Make it yours

Nothing on the board is fixed. Pick a layout preset, then override any part of it in squad's config file.

| Layout preset | What it shows                                            | States                                             |
| ------------- | -------------------------------------------------------- | -------------------------------------------------- |
| team          | rows, detail, replies and the lead's notes (default)     | working · idle · blocked · review · testing · hold |
| crew          | members, the ones waiting on you first, beside the notes | working · idle · blocked · review · testing · hold |
| pr-queue      | one list, oldest first                                   | preparing · ready · sent · merged                  |
| minimal       | name and state only                                      | whatever your lead writes                          |

**team** puts the rows beside the selected member's detail and the latest replies, with the lead's notes underneath. Each row shows the member, its state, its task, its pull request and its model, with what it's waiting on you for on a second line. On a narrow terminal it adapts on its own: the columns shrink, then the model steps aside, then the pull request, and below 100 columns detail and replies fold into their titles so the rows get the room (**d** brings detail and replies back together). A squad that already sets its own `direction`, `panes` or `sizes` under `[squad.<name>.board]` keeps **crew** until you set `layout`.

You can change the panes and their arrangement; add your own **sections**, each a titled list with a filter and a sort; and choose the **columns**, the **states** with their colors and order, and how links open. You also set what every key or click does. A binding is an event (a key like `o`, or `click`, `double-click`) and one line: `jump`, `jump lead`, `back`, `talk`, `reply`, `annotate lead`, `open {pr_link}`, `copy {name}: {task}`, or `run <program> {field}…`, where `{field}` is filled from the row. A section can have its own bindings.

<Code>{`
# ~/.config/tmux-team/squad.toml  (the directory keeps tmt's former name)
[squad.product]
layout = "crew"                        # start from a preset

[bind]
O = "open {issue_link}" # your own key: open the row's issue
`}</Code>

### Layout: rows, lines and panes

A board is laid out the same way at every level, so one set of rules explains all of it. Every row sits on one shared grid of columns, so rows line up and you can compare members at a glance. A row can take more than one line, and on each line a cell can span several columns.

- **Columns** set a width, or `min`/`max` and a `grow` share of what's left; `align`; `truncate` at the `end` or the `middle` (good for paths and links); and a `priority`. On a narrow screen columns first shrink to their `min`; if a row still doesn't fit, the column with the highest `priority` steps aside first, and columns without one never do.
- **Lines**: `lines` says how many lines a row takes and what's on each. Each line lists which columns it uses, and a cell can `span` several columns, so a second line can hold what the member is waiting on you for, under the task. A later line with nothing to show is left out.
- **Where a value comes from**: a column shows the member's squad field of its name, unless `from` binds it to the member's own tmt data: `member`, `presence`, `cwd`, `target`, `session.driver`, `session.model`, `session.usage.tokens`, `session.usage.remaining` (the context window less those tokens, when the driver states a window), `meta.<key>` or `meta.squad.<field>`. The paths are the same for every driver, so a member that switches from Claude to Codex keeps its columns. `format` shows the value as `text`, `tokens` (`487k`), `age` (`5m`) or `count` (`12,345`). Sections, filters and sorts use the same value, and numbers sort as numbers. A missing value shows as `–`, the board's one mark for "nothing here". Squad's own fields (`member`, `role`, `state`, `pending`, `note`) can't be bound. A column can also color its cells by value: `color = [{ at = 400000, token = "review" }, { at = 600000, token = "blocked" }]` gives each cell the theme token of the highest `at` its number reaches. Colors only decorate: the value reads the same without them.
- **Percentage widths** work like CSS. `width = "30%"` is a share of the whole data width, which is the row's width after its marks and the gaps between columns, not of what the fixed columns leave. The percentages you set total at most 100%, and `min` and `max` still count in cells. To split what's left instead, use `grow`, which works like CSS `fr`. A trailing column that no line places takes no width of its own; its value can still fill another cell. When a column steps aside, the shares are worked out again for the rest.
- **By default a cell doesn't wrap.** Text that doesn't fit is cut with `…`, measured by what the terminal draws, so Chinese and emoji line up. Set `overflow = "wrap"` on a column to wrap it onto up to `max_lines` lines (1–8, default 2); the last line is cut with `…` if the text still doesn't fit. Continuation lines start under the cell, and selecting, paging, scrolling and clicking follow the lines you see. A spanned cell uses its first column's settings. The older `[squad.<name>.columns]` form accepts percentage widths and `overflow` too.
- **`tmt sq ls` keeps natural sizing** unless a column it shows uses a percentage width or `overflow`: piped, it never drops or cuts a column. Once a column opts in, the list follows the same fit rules as the board and may truncate, wrap or hide columns. The full values are always in the detail pane and in `tmt sq ls --json`.

<Code>{`
[squad.product.rows]
columns = [
  { name = "member", min = 10 },
  { name = "state",  width = 9 },
  { name = "task",   grow = 1, min = 12 },
  { name = "pr",     width = 10, align = "right", priority = 2 },
  { name = "ctx",    from = "session.usage.tokens", format = "tokens", align = "right" },
]
lines = [
  ["member", "state", "task", "pr", "ctx"],
  ["",       { field = "pending", span = 3 }],   # a second line under the task
]
`}</Code>

**Panes** use the same rules one level up: a split is a row or a column of panes, each with a percentage or a `{ grow = n }` share of what the percentages leave, and splits can nest up to three levels. Tab moves through them in reading order. The `mode`, `direction` and `sizes` keys above are the simple form of it; use one form or the other.

<Code>{`
[squad.product.board]
layout = { direction = "left-right", sizes = [60, 40], panes = [
  "rows",
  { direction = "top-bottom", sizes = [40, 60], panes = ["detail", "notes"] },
] }
`}</Code>

Bindings come only from your own config file, never from what agents write on the board. `run` starts the program directly, not through a shell: each `{field}` fills exactly one argument, so a row can't smuggle in extra commands, and a value that would start an argument with `-` is refused, so it can't slip in an option either. `open` only opens web links. `tmt sq ls` uses the same sections, so the text and JSON views match the board.

**Field providers** fill a column with data tmt doesn't have, such as a pull request's state. A provider runs a program of yours for each member, under the same rules as `run`, and shows its first line of output as a field of its name. The board never waits for one: it shows the last value while providers run in the background, and runs them again after `every`. A failed run shows a dim `?`, never an error. `tmt sq ls --refresh-fields` runs the ones that are due before listing. A program may print `{"value": "#412 open", "color": "review"}` to suggest a theme token for its cell; a column's own `color` thresholds win over it.

<Code>{`
[squad.product.fields.pr_state]
run     = ["gh", "pr", "view", "{pr_link}", "--json", "state", "-q", ".state"]
every   = "60s"
timeout = "5s"
`}</Code>

For the usual case, `preset = "github-pr"` does it for you in place of `run`: it asks `gh` about each member's `pr_link` and shows `#412 open · approved`, `#412 draft` or `#412 merged`. A member without a `pr_link` is skipped; without `gh`, or when it isn't logged in, the column shows `?`.

### State colors and order

Each state's color and place in the list come from `[squad.<name>.states]`, which the layout presets already fill in for their own states. For the states your lead makes up, add patterns:

<Code>{`
[[squad.product.state_patterns]]
match = "blocked*"
color = "blocked"           # a theme token
sort = 0                    # optional: 0-999, lower comes first
ignore_case = true          # optional; off by default
`}</Code>

An exact `states` entry always wins. Otherwise the first matching pattern in file order wins, and a state that matches nothing has no color and sorts after the ranked ones. `match` is a glob over the whole state: `*` matches any run of characters, even none, and `?` matches one character. Everything else is literal. A pattern never changes the state's text. `tmt sq ls` and the board share this order, and in `tmt sq ls --json` a row's `colors.state` is the resolved token, left out when none applies.

### Colors and themes

Color carries meaning, so most of the board stays neutral: only what needs you, what's working and what's stuck stands out. Every color comes from a named **token**, the same set `tmt ls`, the other commands and this site use, and a theme decides what each token looks like. [The design guideline →](/design)

<TokenTable />

Four themes come built in. **tmt** is soft truecolor for dark terminals. **tmt-light** is the same palette for light backgrounds. **terminal** uses your terminal's own 16 colors, so your color scheme decides. **mono** uses only bold and dim. The board also has **auto**, which picks **tmt** or **tmt-light** to match your terminal ([how →](#theming-the-board)). Themes set text colors only, except for the selection (the selected row and tab), so your terminal's background always shows through. Where truecolor isn't available, tmt picks the nearest of your 16 colors; with `NO_COLOR` set, or when output goes to a file or another program, there is no color at all, and every state still shows as text or a mark. The command line keeps your terminal's own 16 colors, so your terminal theme wins, until you set `base` yourself; then commands use your theme too.

<Code>{`
{
  "theme": {
    "base": "tmt",
    "waiting": "#e0a458",
    "accent": "blue"
  }
}
`}</Code>

The theme lives in `~/.config/tmux-team/config.json`. `base` is `tmt`, `tmt-light`, `terminal` or `mono`, and any token can be overridden with a hex value or a color name; `tmt config show` names a key it can't use. It colors the command line once you set a `base`, and always colors the board. `auto` isn't allowed here, because it belongs to the board.

### Theming the board

The board follows the `base` you set for the command line. Until you set one, it is **auto**. A board theme never changes the command line's colors; `tmt config show` shows the command line's theme and its file. Choose a board theme with `tmt sq theme`:

<Cmd>{`
$ tmt sq theme                            # list themes; ● marks the one in use and where it comes from
$ tmt sq theme set auto                   # match your terminal, on every board
$ tmt sq theme set tmt-light              # every board
$ tmt sq theme set mono --squad product   # one squad's board
$ tmt sq theme rm --squad product         # follow the board again; your color tweaks stay
`}</Cmd>

Or press **T** on the board: ↑ and ↓ preview each theme live, **Tab** switches between every board and this squad, **Enter** saves and **Esc** cancels. Either way the choice goes into `squad.toml`, as `[board.theme]` for every board or `[squad.<name>.theme]` for one squad, and the rest of the file stays as it was. A squad's own theme wins over the board's, which wins over the command line's. Each layer can also override single tokens, with the same keys as `config.json`.

**auto** matches your terminal each time the board opens. It reads the `COLORFGBG` variable that many terminals set; without it, the board asks the terminal for its background color. A light background gets **tmt-light**, a dark one gets **tmt**, and when the terminal doesn't answer the board uses **tmt**. The question lasts at most a tenth of a second, so a key you press in that moment is dropped. Listing themes never asks: `tmt sq theme` shows `auto` as `matches the terminal when the board opens`, or as `auto (tmt-light)` or `auto (tmt)` when `COLORFGBG` already says. A theme you choose by name always wins over `auto`.

`auto` works in both `squad.toml` layers and in the picker, where it comes first. Only `config.json` refuses it: with `"base": "auto"` there, `tmt config show` prints `error: theme.base auto only works for the board, not in config.json` with the hint `tmt sq theme set auto`, and the board ignores that setting.

State colors on rows and tab marks are these tokens too: `blocked = { color = "blocked" }`. The older names `red`, `amber`, `green`, `blue`, `cyan` and `magenta` still work. If the command-line theme has a mistake, the board ignores it and says so on its summary line.

### Skills for your lead

Squad comes with a skill for the lead agent. It teaches the lead to read the board, keep it current after every dispatch and reply, and find your settings. When a rule isn't clear, the lead **asks you** instead of guessing. That covers which states to use, what counts as waiting on you, and how members get started. It records what you agree on in its notes, or proposes a config change for you to apply; it never edits your settings on its own.

`tmt extension install squad` offers this skill for the agents you use and asks first.

Optional **playbooks** are example skills for how a lead lays out its team on your host. Today there is one, `tmux-squad` (a leads session and a crew session, one window and worktree per member). Squad never runs it. Read it with `tmt sq playbook show tmux-squad`, then install it, change it, or ignore it.

### Observed age

Squad can show how long it has seen a member's task and state, and the lead's notes, unchanged. It is on in **team** and off in the other layouts; set it per squad with a threshold from one minute to 24 hours. `tmt sq ls` then labels stale rows and notes with their age, and the board dims a stale row with its age at the row's end and puts the notes' age on the notes pane title. The clock starts when Squad first sees the content, so it cannot know how long work sat unchanged before that; editing your config or turning the setting off and on keeps the clock as long as the content has not changed.

<Code>{`
[squad.product.reminders]
enabled = true
stale_after = "30m"
`}</Code>

With Squad's extension hooks enabled (`tmt extension hooks enable squad`) and the provider hook installed through `tmt setup`, Squad can add one short, informational line to the lead's next turn, including when a session starts. It names stale notes, or stale member rows that have shown relevant activity since. Run `tmt sq ls` or open the board to start the observations: until something has been observed, nothing is said. The [Squad skill](https://github.com/pj-tmt/tmt/blob/main/extensions/tmt-squad/skills/tmt-squad/SKILL.md#optional-observed-age) lists the limits.

Turning on these keys installs no provider hooks. Reminder settings in the board are <Tag kind="planned" />.

### Where state lives

Squad keeps its roster and board fields in tmt, with optional observed ages in a disposable local cache. A squad is a tmt meeting room named `squad-<name>`. Each member's state, task and links are stored on its tmt identity. Members started for one job leave the board when their pane closes. Decisions a member needs from you arrive in your inbox, where you can answer them from the board or the command line.

  so there Enter opens the row's actions, as in a plain terminal. cmux is not supported yet.
  Everything else on the board works the same. You can skip this section.
</Callout>

A layout that works well: leads in one place you keep open, members in another, one window and worktree per piece of work. You talk to leads and read the board, and only drop into a member when it needs you. From the board, Enter takes you to that member's screen, even in another session, and `⌫` brings you back.

In tmux, `prefix S` opens the board as a popup that closes when you jump, and `prefix B` keeps it as a pane. `tmt sq hotkeys install` shows exactly what it adds to your tmux config and asks first; `--print` only shows it, and `tmt sq hotkeys rm` takes it out. You can pick other keys: `[tmux] popup = "…"` and `pane = "…"` in squad.toml.

To reach a lead without opening the board, `tmt sq jump --lead` jumps to the lead of the squad you're in (or `--squad <name>`), and `tmt sq back` returns. Add `lead = "J"` under `[tmux]` and install the hotkeys again, and `prefix J` does the same from any member's pane.

| Host           | Jump and back                                 | Where the board opens          |
| -------------- | --------------------------------------------- | ------------------------------ |
| tmux           | to the member's pane, even in another session | a popup on a hotkey, or a pane |
| Herdr          | none; Enter opens the row's actions           | any pane                       |
| plain terminal | none; Enter opens the row's actions           | full screen                    |

### Reference: tabs, refresh and bindings

The full configuration contract is in the Squad skill, which `tmt sq skill show` prints and which lives [in the repository](https://github.com/pj-tmt/tmt/blob/main/extensions/tmt-squad/skills/tmt-squad/SKILL.md). These are the settings people reach for most.

**Tabs.** Beyond `order` and `hide`, `pin` and `colors` shape the tab line:

<Code>{`
[tabs]
pin = ["all"]                # first, in this order, and always in view

[tabs.colors]
waiting = "waiting" # the color of a tab mark when a member waits on you
blocked = "blocked" # and of one with a blocked member
`}</Code>

A pinned tab keeps its place when the tab line scrolls, and the other tabs can't be moved past it. A pinned tab that is hidden or missing is skipped. A color is `default` or a theme token. `squad:<name>` names a squad that shares its name with a built-in tab, such as one called `all`. A hidden squad that you open by name or from the switcher leads the tab line, marked `(hidden)`.

Use `tmt sq ls --tab leads` or `tmt sq ls --tab all` for the same rows in text, or add `--json` for the full tab document. Hidden squads remain included. `--tab` cannot be combined with `--squad` or `--refresh-fields`.

**Refresh.** The board reloads on an interval: 5 seconds unless you set `refresh` under `[board]` for every board, or under `[squad.<name>.board]` for one. Use whole seconds or minutes from `"1s"` to `"60m"`, or `"off"` to reload only on **ctrl-r** and the board's own actions.

**Bindings.** A binding is `event = "action"`. An event is a printable key as you type it (`o` and `O` differ), `enter`, `space`, `tab`, `backspace`, `delete`, `home`, `end`, `pageup`, `pagedown`, `f1` to `f12`, `ctrl-<letter>` (not `ctrl-c`, which always quits), or the mouse: `click` and `double-click`. The keys `q`, `j`, `k`, `/` and `?` are reserved. A section's bindings win over `[bind]`, which wins over the host's defaults. The **leads** and **all** tabs take their own from `[tabs.leads.bind]` and `[tabs.all.bind]`.

| Action                         | What it does                                                           |
| ------------------------------ | ---------------------------------------------------------------------- |
| `jump` · `jump lead`           | go to the row's member, or to its squad's lead                         |
| `back`                         | return to where you were                                               |
| `talk` · `reply`               | write to the member · answer what it waits on                          |
| `annotate` · `annotate member` | note for the lead (the default) or for the member                      |
| `open` · `open {field}`        | open the row's link, or the link in that field                         |
| `copy` · `copy <template>`     | copy a line; the default is `{name}: {task} ({state})`                 |
| `run <program> [args…]`        | start a program; each `{field}` fills exactly one argument             |
| `notes`                        | unfold and focus the notes pane                                        |
| `refresh`                      | reload now                                                             |
| `theme`                        | open the theme picker                                                  |
| `next-pane`                    | focus the next pane                                                    |
| `toggle <pane>...`             | fold or unfold one or more panes: `rows`, `notes`, `detail`, `replies` |
| `menu`                         | open the row's action menu, which Enter does in a plain terminal       |
| `tab`                          | open the row's squad tab, which Enter does on the **all** tab          |

Press `?` on the board for the keys and bindings in effect.
