A driver is what tmt knows about one kind of program. A _host_ driver knows where agents live and how to type into them. A _runtime_ driver knows one agent program: how it starts, resumes and reports its conversations.

**The drivers most people need are built in. There is nothing to install.** tmt recognizes the program you start and uses the matching driver automatically:

<Cmd>{`
$ tmt run reviewer claude        # name this pane "reviewer" and start Claude Code in it
$ tmt run builder codex          # same for Codex
$ tmt setup                      # optional: connect every agent found, after your OK
`}</Cmd>

Without setup, every agent still works: tmt talks to it through its pane. `tmt setup` adds what only the agent itself can tell tmt. It learns which conversation belongs to which name, so `tmt resume` reopens the right one, and a short "who you are and what's waiting" summary is given at start. `tmt setup` shows exactly which settings it will change and asks first; `tmt setup claude` or `tmt setup codex` does the same for one agent, and `--remove` undoes it.

| Driver      | Kind    | Works without setup                                                         | After `tmt setup`                                                        |
| ----------- | ------- | --------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| tmux        | host    | everything                                                                  | nothing more needed                                                      |
| Claude Code | runtime | talk, reply, `tmt run`                                                      | exact resume, start-of-session context, running/ended state              |
| Codex       | runtime | talk, reply, `tmt run`; on a shared server it asks for `--identity` instead | exact resume, exact thread match on a shared server, running/ended state |

### The built-in drivers

- [tmux](/drivers/tmux): the host driver. Where agents live and how to type into them.
- [Claude Code](/drivers/claude-code): a runtime driver, with exact resume, start-of-session context and an optional message channel.
- [Codex](/drivers/codex): a runtime driver, safe even when several panes share one Codex server.

### Herdr: ships with tmt, approve once

The Herdr host driver comes with tmt, but it runs only after you approve it. `tmt driver install herdr` shows what it will run and asks first:

<Cmd>{`
$ tmt driver install herdr   # shows what it will run, then asks
$ tmt driver ls              # herdr: ok, changed or missing
`}</Cmd>

The approval carries over when tmt upgrades, as long as the new driver asks for nothing more. If it asks for more, `tmt driver ls` shows it as changed, with the reason, and `tmt driver install herdr` approves it again. Until you approve it, commands run in a Herdr pane print a hint once a day, and Herdr bindings wait without being deleted.

### Usage counters

Usage is opt-in. `tmt setup --usage` (or `tmt setup claude --usage`, `tmt setup codex --usage`) also adds a hook that runs when a turn ends and records how much the agent has used:

- **Context size**, in `resume.usage`: `tokens` is what the next request re-sends, and `windowTokens` is the context window when the provider states it (Codex does, Claude Code doesn't).
- **Consumption**, in `resume.consumption`: the tokens of completed requests. `inputTokens` includes cached input, `outputTokens` is the output, reasoning included, and the total is input plus output.

Both show in `tmt ls --json` and `tmt identity show --json`, and an [Ops](/extensions/squad) column can show the context size. Only token counts are stored, never the conversation. The hook also lets `session.activity` return to idle when a turn ends; without it, tmt never guesses idle from silence. `tmt setup --no-usage` removes only this hook.

Read the numbers as tokens, not cost. They describe completed requests, not live streaming, and can lag a turn behind. Each counter starts at its first reading and never counts earlier history. A missing counter means unavailable, never zero. A tool that works out rates should start a new baseline on the first reading, when `epoch` changes, when `gap` is true or when a counter goes down.

### More drivers <Tag kind="planned" />

Every other driver will be its own package with its own version, installed and updated like an extension. Anyone can publish one: a driver is a program named `tmt-driver-<name>` that answers tmt's driver protocol, and the built-in drivers sit behind the same interface. A driver you install can also take over from a built-in one, for example a Claude Code driver with extra features. `tmt driver ls` then always shows which driver handles which program.

<Cmd>{`
$ tmt driver install ./tmt-driver-screen  # shows what it will run, then asks
$ tmt driver ls                          # approved host drivers: ok, changed or missing
$ tmt driver rm screen
`}</Cmd>
